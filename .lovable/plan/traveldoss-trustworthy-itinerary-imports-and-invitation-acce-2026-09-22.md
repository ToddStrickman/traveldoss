Goal: preserve every supplied detail, assign days/dates/structure accurately, and ensure imports either complete correctly or fail honestly with recoverable source. Preserve current collaboration, layout, print and offline work, and the separate Adaptive Trip Dossier integration plan.

## 1. define import correctness before changing the model
Make lossless source preservation and faithful structuring the foundation. Separate "import what I supplied" from explicit "generate/improve my trip." Imported material is data, including embedded instructions; it must not override system rules or trigger tools/actions. AI may classify/group and propose uncertain associations, but must not invent bookings, venues, dates, costs, transport, or times, reorder the user's plan, or resolve conflicts silently.
Keep trips.content.blocks the canonical editable itinerary, with backward-compatible provenance/metadata. Validate typed blocks and allowed metadata at every write boundary; replace z.any() acceptance with a versioned compatibility-aware contract so model validation cannot be bypassed by a direct client write. Preserve the original source privately with stable source segment IDs/spans and parser/schema version; it is evidence, not a second editable itinerary. Specify the protected source location, access policy and retention/deletion behavior; do not put the private raw-source archive into public or unlisted dossier responses, PDF exports, service-worker caches or analytics by default. Preserve the full meaningful text, tables/cells, lists, URLs, costs/currencies, narrative, alternatives, reservations and every transport leg. Rich source can remain as visible narrative/table blocks when structured fields cannot represent it. Sanitise rendering and URLs; do not render arbitrary source HTML. Unsupported/ambiguous content must remain visible with an actionable warning, never disappear into a debug download.
Define dates carefully: distinguish day number, calendar date, local time, time zone and overnight arrival; no made-up year or midnight placeholder. Keep conflicting or underspecified dates as supplied with a focused correction request. Repeated hotel/restaurant visits on different days are distinct occurrences.
Build a source coverage ledger and authored fixture fact assertions. All source segments must be accounted for in accessible content or explicitly unresolved. A raw archive, model self-confidence score, matching block count, or claimed segment reference alone is not proof of semantic correctness. Unknown fields/kinds and missing required values must produce preserved residual content or validation errors with source location, not filter(Boolean) loss.

## 2. trace and repair the entire path
Document the actual paste/upload/transcript entry points and supported file types; do not quietly broaden this into a new PDF/OCR product. Follow input -> extraction -> deterministic/AI parsing -> normalization -> conversion -> save-time enrichment -> persistence -> reload -> shared itinerary projections -> Vertical/Horizontal/Grid, existing PDF/print and offline output.
Use deterministic, lossless CommonMark/GFM handling for recognisably structured Markdown and a tested path for plain text/transcripts. Do not mistake every indented Day N line for a Markdown heading. Use AI only where interpretation is needed, retaining source independently of model output.
Protect imported source and manually edited fields from automatic refine/harden passes, field-whitelisting and enrichment. Optional concise editorial notes are additive; never replace the traveler's original note. Background suggestions must be field-scoped, attributed, reversible, and unable to overwrite newer user edits. Model knowledge and model self-review must not be labelled verified; verification requires evidence or explicit user confirmation.
Keep geocoding/place lookups/note synthesis bounded and optional, with per-stage deadlines. Their failure must not discard the imported source or block saving a valid structured result. Prevent link-title lookups from dereferencing arbitrary private/internal source URLs. Fix every-flight-leg rendering and day/appendix placement in shared components, keeping existing skins and old trips compatible.

## 3. responses transport and long inputs
Retain the assigned openai/gpt-6-astra via the Lovable gateway. First verify the CURRENT gateway-specific Responses endpoint, authentication header, exact model identifier, mandatory reasoning settings, structured-output support, run-ID propagation and installed client compatibility with a minimal capability probe. Do not infer gateway support from direct OpenAI support or invent a reasoning setting. Document the verified contract in the implementation evidence.
Use streaming server-side and a shared adapter for parsing and optional note synthesis. Use the current Responses text.format structured schema contract, keep runtime validation authoritative, and align nullable/required properties and additionalProperties semantics with strict schema requirements. Use stateless request options (store:false; no previous_response_id or conversation reuse) and only supported parameters. Never expose keys or model reasoning in the browser.
Prefer an existing compatible typed streaming client; if parsing SSE directly, test fragmented UTF-8, CRLF, comments, multiple events per chunk, partial frames, output/content indices and final flush. Accumulate only the intended output text, without appending the completed payload twice. Success requires a completed terminal response and a fully validated result; handle incomplete, failed, error, refusal, disconnect, empty output and client cancellation separately. Cancel/close upstream work and release readers on abort/deadline.
Replace the fixed 8192 whole-document output cap with a tested, bounded capacity strategy. Inventory model AND gateway AND hosting input/output/body/runtime limits, including reasoning-token allowance. State concrete supported input limits and what the user sees above them. Preflight large inputs and split at stable section/day boundaries when needed, with global date/destination context and careful carryover for multi-day lodging/overnight flights. Merge by source identity/order, not name-based deduplication. Test overlap removal, missing chunks and duplicate chunks. Use bounded concurrency and total request/time/cost budgets. Do not promise unlimited documents or assume 30 days always fits one output.
Retries must be classified: bounded Retry-After-aware backoff with jitter for permitted transient statuses/transport failures; no unchanged retries for schema errors, refusals, invalid credentials, exhausted credits or deterministic truncation. A truncation recovery must actually change the work (smaller chunks/budget strategy), never concatenate a new attempt onto a partial old one. No partial model stream is persisted as a completed trip. Use existing job machinery if the verified runtime requires it; avoid inventing a distributed job system unless measurements justify it.

## 4. honest, recoverable product behavior
Use explicit states (reading, structuring, validating, ready, needs review, failed/cancelled) and useful progress for long inputs. Preserve submitted content across recoverable errors; cancellation, double-clicks, retries and late responses cannot create duplicate dossiers or overwrite a newer attempt. Use an import/idempotency identity and concurrency control for saving.
A faithful deterministic parse can succeed without AI. A degraded or incomplete parse cannot display the ordinary success/mint path. Keep the existing dossier-as-review experience where practical; show unplaced source and specific corrections there in a recoverable draft. No silent destructive replacement of an existing trip and no automatic publication/payment as failure recovery. Preserve the last good saved version.
Sanitised telemetry should identify stage, parser/model/schema version, input/output sizes, terminal status/incomplete reason, retries, duration, coverage counts and gateway run ID. Distinguish model, schema, persistence and rendering failures. Remove raw itinerary/model output from routine console/analytics errors, including current raw snippets and field-value diagnostics. Debug exports, if retained, are private, explicit, sanitised and scoped; no tokens, credentials, email addresses or travel details in shared logs/analytics.

## 5. invitations: database invariant plus transactional state transition
Keep a NEW forward migration; never edit a deployed migration. Inspect actual deployed schema and data read-only first. Preflight lower(trim(email)) collisions, blank/invalid historical data and owner/active/removed/user-id conflicts. Define safe reconciliation preserving membership identity, role and references; do not silently delete or merge different accounts.
Enforce canonical email consistently on all future writes at the database boundary as well as application entry points. Backfill safely and create a real nondeferrable UNIQUE(trip_id,email) compatible with the shared conflict target, plus appropriate canonical/nonblank checks. Plan the lock/transaction and constraint replacement order so concurrent writes cannot open a uniqueness gap. Include schema-cache compatibility checks, generated types where needed, and a forward recovery procedure.
Implement acceptance as ONE transactional database operation (or equivalently verified transactional boundary): derive identity from trusted auth, validate the invited/verified email according to the actual Auth configuration, lock and recheck the invitation, expiry/revocation and target trip, activate the intended membership, and consume the invite together. Roll back everything on failure. Restrict any SECURITY DEFINER function's search_path and execution grants and enforce authorization inside it; never trust a caller-supplied user ID/email. Test ordinary authenticated roles, not only service_role.
Make repeat acceptance idempotent for the same already-authorised recipient while denying another identity; require the current membership to still be active so replay cannot resurrect removed access. Coordinate acceptance/revoke/remove races. Reinviting an active member must not demote the owner, downgrade the member to invited, change the bound account, or reset joined_at. Define resend/reinvite policy explicitly (replacement invalidates prior pending tokens; removed members need a new owner-authorised invite). Multiple recipients need per-address outcomes and retry identities.
Create the invitation and any pending roster row atomically; check every error. Send email only after successful commit and report delivery status separately. Delivery retry must not create duplicate invitations or revoke a successfully delivered link accidentally; use the existing delivery mechanism with idempotency, adding an outbox only if required. Acceptance success requires the committed membership and a usable destination, not just zero database errors. Preserve hashed single-use token handling, safe login return navigation, view-only share links, owner-only actions and locked/expired trip rules.
